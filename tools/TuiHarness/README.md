# TuiHarness

Runs the Wingman TUI headless on the ANSI driver at a fixed size against the fixture-backed fake, plays the scripted keys in `Program.cs`, and quits.
Run it with `dotnet run --project tools/TuiHarness -- 96 30 Midnight` (width, height, theme).
Every step appends a frame to `tools/TuiHarness/out.txt`, the screen dump: the text rows, and for some steps a map of one letter per cell with a legend of its colors.
It compiles the `src/Wingman.Tui` sources directly, so it sees internal types; it is not in `Wingman.sln`.
Steps can also check what their frame shows; each check appends a `check ok` or `check FAILED` line after the frame, and the harness exits with 1 when any check failed.
After the main scenario the harness starts itself again once per child scenario, each appending its frames to the same `out.txt`; the main run fails when any of them does. `--elevated` tells the shell it already runs as administrator and plays a short scenario of its own (the title bar badge, the queue pane and batch screen, Retry elevated refused, the dim restart action). `--route update-all`, `--route history`, and `--route no-such-tab` open the shell on a start route: Updates with every update marked and the run question, History, and the first tab with the unknown-route status. Restart as administrator goes to a stand-in that records the arguments and reports the prompt declined.
The shell gets stand-in host services: `RecordingSetupExecutor` records each plan and reports every item created (or removed), so the Settings tab's register and remove actions never touch Task Scheduler or the registry, and `RecordingSelfUpdateStarter` only counts calls. `SlowClient` reports Wingman itself as `9.9.9` against the harness's `1.0.0`, so the startup check finds an update; the main run ends by pressing `Update Wingman`, which must call the starter and stop the app, and a run still going three seconds after its last step fails. The route runs leave the self-update check out, since its status would replace the one a route posts.
The run points `WINGMAN_DATA_DIR` at a temp folder, seeds `package-options.json` there with machine scope and a post-update command for `Microsoft.Azd` so the queue pane shows `⚡ admin`, and deletes the folder at the end, so it never touches the real settings, package options, or history; batches write their history into its `history` folder, which the checks read, and one step adds a hash-mismatch entry there for `JanDeDobbeleer.OhMyPosh` so the update policy dialog shows its suggestion to exclude it. Pre- and post-commands go to `FakeCommandRunner`, which prints one line instead of starting a shell, and batches that need elevation go to `HarnessElevation`, a stand-in for the helper launcher that connects at once to a channel running each operation on the same fake client; one step has it keep the prompt "up" for 300 ms and then report it declined.
Mouse steps inject clicks, double-clicks, right-clicks, and wheel events at screen cells. The run swaps in a fake clipboard and a URL opener that only records, so `Copy id` and `Open homepage` never touch the real clipboard or start a browser.
`--svg <outputDir>` also writes the frames of the steps given a `Screenshot` name to `<outputDir>/<name>.svg`: the loaded Installed tab (`installed`), Updates with the queue pane (`updates`), and a batch mid-run (`batch`). Each SVG draws the cells at 9x18 px (864x540 at 96x30) inside a rounded window frame, with one rect per run of equal background and one text per run of equal foreground whose `textLength` spans its cells, so columns line up in every browser. The README's screenshots come from `dotnet run --project tools/TuiHarness -- 96 30 Midnight --svg assets/screenshots`.
Some checks compare the frame the main loop drew incrementally between steps with the full redraw `Dump` forces, which catches views that only look right when everything is drawn again. At 96x24 the driver was back at 120x30 between steps, which breaks those checks and the mouse coordinates; 96x30 and 120x40 keep their size.
